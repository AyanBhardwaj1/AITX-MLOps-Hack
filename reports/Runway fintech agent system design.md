# Build the waste-to-runway loop Rho lacks

Runway's winning move is to close the loop that no bank-native product closes today: read Rho transactions, turn them into a subscription inventory, price each piece of waste as **extra days of runway**, and hand the founder a drafted action or a filed Jira ticket. Ramp, Brex and Digits all ship agents, but each works only on spend running through its own cards or ledger, while Rho and Mercury expose raw read-only data (API and MCP) with no opinionated layer on top. The research confirms most of PLAN.md and changes it in five places. First, Rho's sandbox is a **static set of 72 transactions with only two ~$18 software charges**, so the seeded "Taco Robotics" ledger is the real demo, not a fallback. Second, Rho's actual schema differs from the types already in `src/lib/types.ts`: statuses are `pending | settled | failed | awaiting_approval`, `id` is not unique per row, and a `/cards` endpoint with cardholders and spending limits does exist. Third, a prior Rho hackathon team already built "find subscriptions, look up pricing, renegotiate", so Runway has to win on the runway delta, goal-seek planning, Autopilot with Jira, and a published eval. Fourth, the Copilot is cheaper to build on the Vercel AI SDK v7 than on a hand-rolled OpenAI loop, while Autopilot should stay a fixed, deterministic pipeline. Fifth, adding `org_id`, a findings fingerprint and an agent-run log now costs minutes and makes the schema production-shaped. Everything below is sized for a 1–2 person team with features frozen Wednesday night and the submission due Thursday, Oct 29.

## Incumbents ship agents and benchmarks, but nobody bank-native closes the loop

The 2026 finance-software market has converged on three things Runway should borrow, and has left one gap open. The first is agents that act on spend. Ramp launched procurement agents in April 2026 that cover **renewal tracking**, followed by purchasing agents and **token spend management** in Q2 ([Crowdfund Insider](https://www.crowdfundinsider.com/?p=207415)). Brex ships an Audit agent that ranks violations by risk and a Review agent that auto-approves low-risk items and escalates the rest ([Brex](https://brex.com/intelligence)). Digits' accounting agents "pause for human input" mid-workflow ([Accounting Today](https://accountingtoday.com/news/digits-says-its-new-ai-agents-can-automate-95-of-bookkeeping-tasks)). The second is peer price benchmarks built from the vendor's own transaction network: Ramp Price Intelligence draws on "millions of Ramp transactions" ([Ramp support](https://support.ramp.com/hc/en-us/articles/17522214341523-Price-Intelligence-on-Ramp)), and Vendr's free tier gives SKU-level benchmarks for 50+ suppliers ([Vendr](https://vendr.com/software-prices)). The third is scenario planning. The FP&A product formerly called Runway, now CFO.ai, branches main, upside and downside cases through its agent "Ari" for $295/month ([runway.com](https://runway.com/llm-info)).

The gap sits in the bank-native tier. Rho's API and Claude connector are read-only, with no money movement and "deeper agent workflows are coming" ([Rho help center](https://www.rho.co/help-center/the-rho-api)). Mercury's VP of Product says early MCP users are **building "reports, burn-rate views and invoice flows" themselves** on raw MCP access ([implicator.ai](https://www.implicator.ai/editors-picks/)). That is direct evidence of unmet demand for the opinionated layer Runway provides. Ramp's waste findings are real, but they live on Ramp: Eight Sleep was "automatically notified of duplicative spend" and saved more than $5,000 on AWS ([Ramp](https://ramp.com/customers/eight-sleep)). A founder who banks with Rho gets none of this without migrating cards.

The prior-art check is sobering in one place. Devpost projects like RunwayPilot ([Devpost](https://devpost.com/software/runwaypilot)) and RunwayIQ, which chains three Claude calls over an uploaded CSV ([Devpost](https://devpost.com/software/runwayiq)), are shallow: CSV input and LLM-computed numbers. The real competitor is **rhodesk**, built at an earlier Rho hackathon. It is a subscription-renegotiation agent on Rho that hit the same sparse-sandbox wall and added an 18-month synthetic ledger badged "demo" ([rhodesk](https://github.com/manojmaheshwarjg/rhodesk)). Runway must therefore not pitch itself as "we find subscriptions and look up prices". The differentiators that survive are the runway delta ("these six cuts buy you 2.1 months"), goal-seek planning, an Autopilot that files owned and dated Jira tickets, and published precision and recall on planted waste.

Two smaller risks matter for the pitch. "Runway" collides with CFO.ai's former brand and with runway.com ([runway.com](https://runway.com/llm-info)), so the README and table sign should say "Runway for Rho" or similar. Ramp's 2026 move into token-spend management ([Crowdfund Insider](https://www.crowdfundinsider.com/?p=207415)) also marks **AI and LLM API spend as a new waste category**, which lands well with Austin AI-startup judges. The existing `ai_api` category in `src/lib/types.ts` already supports it.

## Rho's 72-transaction sandbox makes the seeded ledger the real demo

### What the API really returns

Rho's v1 API is a small GET-only REST API at `https://rhoapi.rho.co/api/v1`, with a sandbox at `rhoapi-sandbox.rho.co` that accepts any non-empty bearer token ([Rho docs](https://docs.rho.co/docs/v1/getting-started)). Every write returns 405 ([rhodesk](https://github.com/manojmaheshwarjg/rhodesk)). Working client code from earlier hackathon teams shows more surface area than PLAN.md assumes: `/accounts`, `/transactions`, `/transactions/{id}`, **`/cards`**, `/statements`, `/invoicing/customers` and `/invoicing/invoices` ([rhodesk rho.py](https://github.com/manojmaheshwarjg/rhodesk/blob/HEAD/rhodesk/rho.py)). The OpenAPI document is served at `/api/v1/openapi.json`, and **there is no JavaScript SDK**, so a hand-written fetch client is the intended path ([LockInVowe client.ts](https://github.com/AnuRaghav/LockInVowe/blob/HEAD/lib/source/rho/client.ts)). If organizers hand out a hackathon-specific SDK, nothing about it is public yet.

The transaction object carries `id, account_id, amount {amount, currency}` in signed minor units, `status` (`pending | settled | failed | awaiting_approval`), a free-text `transaction_type`, `counterparty_name`, `initiated_at`, `posted_at`, `memo`, `note`, and optional `card_id`, `card_name`, `user_id` and `user_full_name` ([LockInVowe client.ts](https://github.com/AnuRaghav/LockInVowe/blob/HEAD/lib/source/rho/client.ts)). Four details break naive code. **There is no MCC or merchant category**, only `counterparty_name` ([RhoHack](https://github.com/evapisk/RhoHack)). **`id` is not unique per row**, because legs of one money movement can share it, so the key must be `(id, account_id)` ([rhodesk rho.py](https://github.com/manojmaheshwarjg/rhodesk/blob/HEAD/rhodesk/rho.py)). Rho fills `posted_at` even on failed rows, so failed rows must be excluded explicitly, never by checking for a null date ([RhoHack](https://github.com/evapisk/RhoHack)). And settled amounts can differ from the authorization, so amount is a mutable column ([Rho docs](https://docs.rho.co/docs/v1/transactions)).

Pagination is cursor-based with `page_size` up to 100 and an opaque `next_page_token`. Cursors are bound to the filters they were issued with, and Rho tells clients not to store them ([Rho docs: Pagination](https://docs.rho.co/docs/v1/pagination)). Teams found that unknown query parameters are silently ignored, and that **an empty filter value such as `initiated_before=` returns 200 with zero rows** ([rhodesk rho.py](https://github.com/manojmaheshwarjg/rhodesk/blob/HEAD/rhodesk/rho.py)). The limit is about **60 requests per minute per token and 600 per minute per source IP**, with no webhooks, so sync has to poll ([Rho docs: Rate limits](https://docs.rho.co/docs/v1/rate-limits); [Rho blog](https://www.rho.co/blog/best-banking-apis-for-business)). Production tokens use the prefix `rhobat_` and expire within a year ([RhoHack](https://github.com/evapisk/RhoHack); [Rho auth](https://docs.rho.co/docs/v1/auth)). The two scope pages disagree on naming, so check each endpoint's Security section once production access arrives.

### Why the sandbox cannot carry the demo

Analysis of a checked-in copy of the live feed shows **exactly 72 transactions dated 2023-05-31 to 2026-06-26**, identical on every call. They break down as 61 settled, 8 failed, 2 pending and 1 awaiting approval, and the only SaaS-like spend is "Teamline Software, Inc." at $17.50 and "Cloudbridge Services LLC" at $18.50 ([RhoHack fixture](https://github.com/evapisk/RhoHack/blob/HEAD/backend/fixtures/sandbox_transactions.json)). Two consequences follow, and PLAN.md captures only the first. The detectors cannot fire on sandbox data, so the Taco Robotics seed is the main dataset. Less obviously, **the sandbox's newest row predates today by four months**, so a "trailing three complete months" burn computed as of Oct 27 sees zero spend and reports infinite runway. Sandbox mode should therefore compute as of the latest transaction date and label it that way. The sandbox also has six `credit_repayment` rows alongside `card_debit` rows on Credit Accounts ([fixture](https://github.com/evapisk/RhoHack/blob/HEAD/backend/fixtures/sandbox_transactions.json)). If card purchases and the checking-account payments that settle them both count as outflows, burn is double-counted, so repayments belong in the transfers bucket.

The right framing is the one rhodesk used: a deterministic overlay ledger in Rho's exact schema, **visibly badged "demo"**, next to the real sandbox rows. Judges respect that transparency, and disguising seeded data would hurt.

### Features the real schema unlocks

Because cards and cardholders exist, three ideas in PLAN.md's open questions become cheap. The first is **owner attribution**: `user_full_name` on a SaaS charge tells Autopilot whom to assign the Jira ticket to. The second is **cross-card duplicates**, the same tool paid on two cards, which is exactly the pattern rhodesk planted with Asana ([rhodesk fixtures.py](https://github.com/manojmaheshwarjg/rhodesk/blob/HEAD/rhodesk/fixtures.py)). The third is **card-limit recommendations** from `/cards` `spending_limit`, which is the natural first write action once Rho opens writes. The `awaiting_approval` status adds a fourth, an "approve-before-you-pay" checkpoint: "this $X renewal is pending approval, and a cheaper plan exists." Rho Treasury quotes yields up to 4.55% as of August 2026 ([Rho llms-full.txt](https://www.rho.co/llms-full.txt)). That supports a sponsor-friendly **idle-cash insight**, which must be labeled as an estimate because the minimum balance is quoted as both $50K and $100K.

### Apify and Jira: what to call and what to avoid

For pricing pages, Apify's **RAG Web Browser** takes a URL as its `query`. Passing a URL skips the search charge, failed loads are free, and browser rendering returns LLM-ready markdown in **16–31 seconds** depending on memory ([RAG Web Browser README](https://github.com/apify/rag-web-browser/blob/HEAD/actors/apify_rag-web-browser/README.md)). The synchronous `run-sync-get-dataset-items` endpoint hard-fails with HTTP 408 after 300 seconds ([Apify OpenAPI](https://github.com/apify/apify-docs/blob/HEAD/apify-api/openapi/paths/actors/acts@%7BactorId%7D@run-sync-get-dataset-items.yaml)). The `apify-client` `call()` accepts `maxTotalChargeUsd` to cap spend ([apify-client-js](https://github.com/apify/apify-client-js/blob/HEAD/src/resource_clients/actor.ts)), and the free plan gives $5 a month ([Apify pricing](https://apify.com/pricing.md)). Use `scrapingTool: 'browser-playwright'`, because most pricing pages render client-side behind monthly/annual toggles. Scrape ahead of time, cache the markdown and the extracted tiers in Supabase with a timestamp and source URL, and **never scrape live during judging**.

Jira Cloud tickets are a single `POST /rest/api/3/issue` with Basic auth (`email:api_token`). The **`description` must be Atlassian Document Format; a plain string returns 400** ([Jira REST v3](https://developer.atlassian.com/cloud/jira/platform/rest/v3/api-group-issues/); [atlassian-cli guide](https://atlassian-cli.pages.dev/blog/jira-rest-api-guide)). Descriptions over 32,767 characters fail but still burn an issue number ([JRACLOUD-78553](https://jira.atlassian.com/browse/JRACLOUD-78553)). The points-based quotas Atlassian began enforcing on March 2, 2026 **do not apply to API-token traffic**, which is subject only to burst limits ([Jira rate limiting](https://developer.atlassian.com/cloud/jira/platform/rate-limiting/)). Raw `fetch` with a hand-built three-node ADF document is less code than adding `jira.js`. Make filing idempotent by keying each ticket on the finding's fingerprint, both as a Jira label and as a unique column in the database, so a cron retry never files duplicates.

## Merchant-level labels and SQL detectors keep every dollar auditable

### Normalize first, then label vendors rather than transactions

The literature is blunt about LLM-only categorization. On abbreviated SME bank descriptors, **zero-shot GPT-4o reached about 60% accuracy against 73.5% (±5.1) for a trained method** ([arXiv 2508.05425](https://arxiv.org/html/2508.05425v1)). Mercado Libre reported roughly 60% for regex, 80% for GPT-3.5 and 90% for custom embeddings ([ZenML](https://zenml.io/llmops-database/financial-transaction-categorization-at-scale-using-llms-and-custom-embeddings)). Vendor claims above 90% exist, but Ntropy itself warns buyers not to trust published accuracy numbers ([Ntropy](https://ntropy.com/blog/evaluations-part-three)). The useful structural fact is Ntropy's report that the **top ~500 merchants cover about half of all transactions** ([Ntropy](https://www.ntropy.com/blog/transaction-intelligence-is-a-solved-problem-but-how-much-does-it-cost)). A curated catalog therefore wins on the head of the distribution, and the LLM only needs to handle the tail.

That points to the pipeline the repo has already started in `src/lib/vendors/normalize.ts` and `catalog.ts`. A regex pass strips processor prefixes (`SQ *` Square, `TST*` Toast, `PAYPAL *`, `SP *` Stripe) ([statementdecoder](https://statementdecoder-web.onrender.com/blog/bank-statement-descriptor-anatomy)) along with order IDs, which otherwise make one merchant look like many ([Monzo community](https://community.monzo.com/t/split-identifiers-from-merchant-name-in-descriptors/1985)). An alias lookup against the catalog follows, then an optional `pg_trgm` similarity match, and only then a batched cheap-model call on the **unique merchant keys**, never on raw transactions. One vendor can appear as "GITHUB.COM", "GITHUB *COPILOT" and "MICROSOFT *GITHUB" ([Slash](https://www.slash.com/charge-identifier/github)), so the catalog's alias lists do real work. Rho's `counterparty_name` is cleaner for ACH and wires than card descriptors, so the regex mostly matters for card rows. Ramp's production merchant-correction agent keeps string matching alongside embeddings for the same reason: "card acceptor names can be vastly different from actual merchant names" ([Ramp builders](https://builders.ramp.com/post/fixing-merchant-classifications-with-ai)).

The labeling call should return a closed enum through structured outputs: category, a `job_to_be_done` sub-label for SaaS (video_conferencing, docs_wiki, llm_api and so on), `is_saas`, `billing_model` and a confidence score. Run it at temperature 0, cache it by `(merchant_key, prompt_version)`, and **escalate to the mid-tier model only when confidence is below 0.6**. That two-tier pattern mirrors Parafin's production setup ([Parafin](https://www.parafin.com/blog/why-two-llm-agents-beat-one-on-financial-classification)). The job-to-be-done label is what makes duplicate-tool detection possible, and a spreadsheet cannot do that.

### Recurrence and waste are a few window functions

Plaid's recurring product groups by description, amount and cadence. It calls a stream **mature at three or more occurrences** and surfaces newer ones as `early_detection` ([Plaid](https://plaid.com/blog/recurring-transactions/)). An open spec adds concrete tolerances: weekly 7±2 days, monthly 30±5, quarterly 90±10 and annual 365±15, with amount stability at a coefficient of variation of 0.15 or less ([expense-tracker #52](https://github.com/Ankush82/expense-tracker/issues/52)). Real streams wobble by cents and by a day or two ([plaid_finance_radar](https://github.com/fadeel7/plaid_finance_radar)), so collapse same-vendor charges within three days into one charge event before computing gaps. Annual plans rarely reach three occurrences in 12–18 months of history. Accept two charges about a year apart as `annual, early_detection`, or a single large charge from a vendor the LLM tags as annual SaaS as `suspected_annual`, and put those renewals on the runway calendar because they are lumpy cash events. Usage-billed vendors such as AWS and OpenAI are recurring by cadence but variable in amount. Exclude them from price-creep alerts and watch them with anomaly scores instead.

Four detectors run as plain SQL over the streams table. **Price creep** flags a fixed stream whose last charge is at least 10% and at least $20 a month above the median of its first three charges, persisting for two consecutive charges so a one-off proration does not trigger it. **Duplicate tools** groups active streams by job-to-be-done and flags groups with two or more distinct vendors, with an allowlist for intentional pairs such as AWS plus Vercel. **Zombies** have to be honest about the data: bank rows show no usage, so a "likely zombie" is a duplicate-group loser still billing 60+ days after its replacement started, a charge tied to a departed cardholder, or a never-changed fixed stream with an annual renewal coming up. Show the reasons, and let the user mark a tool unused. **Anomalies** use the modified z-score `0.6745 × (x − median) / MAD` with a cutoff of 3.5, because classical z-scores are bounded for small samples ([NIST e-Handbook](https://itl.nist.gov/div898/handbook/eda/section3/eda35h.htm)). When MAD is zero, which is common for fixed subscriptions, fall back to a percentage rule. Duplicate charges (same vendor and amount within three days) and new large vendors are cheap extras. Isolation forests are overkill: there are no labels, the volume is under 1k rows, and a CFO cannot audit them.

### Burn, runway and forecasts

Practitioner sources agree on net burn as gross outflows minus customer collections. They also agree that runway is cash on hand divided by a **trailing three-month average**, because a single month misleads: Mercury's worked example moves from 10 to 11.1 months of runway when one lumpy payment is averaged out ([Mercury](https://mercury.com/blog/calculate-startup-cash-burn-rate); [Pilot](https://pilot.com/blog/burn-rate-calculation-startup-runway-calculator)). Conventions vary, and Kruze effectively uses gross burn ([Kruze](https://kruzeconsulting.com/startup-runway)), so the UI should state which one Runway uses. Exclude internal transfers, card repayments, equity raises and loan proceeds. Flag one-offs and show "excluded: $X across N items" so the user can toggle them. `src/lib/finance/runway.ts` already averages complete months and returns a zero-cash date. What it lacks is the sandbox as-of fix, Rho's real status values and the one-off toggle.

For forecasting, skip Prophet and ARIMA: 6–24 monthly points overfit. A component projection is easy to explain. Fixed streams sit on their predicted dates, including annual renewals; variable streams use a trailing median; and inflows use a trailing average. Three scenarios (base, cut flagged waste, downside) give the headline "+N days if you act" number. A bootstrap Monte Carlo producing P10/P50/P90 zero-cash dates is about 30 lines of TypeScript and makes a strong production-phase upgrade.

### The eval is the "not a wrapper" proof

No public labeled dataset of startup spend with planted waste exists. The closest are consumer and fraud generators ([Mendeley](https://data.mendeley.com/datasets/ktbthg777x/1); [Gretel on Azure](https://ai.azure.com/catalog/models/Gretel-Navigator-Tabular)). The seed generator therefore doubles as the benchmark. Plant labeled duplicates, zombies, step and gradual price creep, and anomalies. Add **negative controls that must not fire**: AWS plus Vercel, prorations, annual renewals and normal usage variance. Generate three to five seeded companies at two noise levels (clean descriptors versus prefixed and truncated ones), so results carry a spread rather than a single number, following the mean ± std reporting of the SME paper ([arXiv 2508.05425](https://arxiv.org/html/2508.05425v1)). Report per-detector precision and recall, **dollar-weighted recall** (the share of planted wasted dollars found), categorization accuracy and macro-F1 against a rules-only baseline, cache hit rate, and dollars per 1k transactions. For the Runway Review memo, a deterministic check comes first: every dollar figure and date in the memo must appear in the SQL results. That makes **hallucinated numbers zero by construction**. An LLM judge is optional on top, and it should use position swapping and a locked rubric ([Openlayer](https://www.openlayer.com/blog/llm-as-judge-evaluation-guide.md)).

## One tool registry, two agents, and a plan-then-execute Autopilot

### Models and API surface

The GPT-6 model IDs in PLAN.md are real. The `openai@7.45.0` type union lists `gpt-6-astra`, `gpt-6.1-sol`, `gpt-6-sol` and `gpt-6-luna`, and **there is no `gpt-6.1-luna`**. `gpt-6.1-terra` appeared on Oct 26 and fails the two-week dependency rule ([openai npm](https://www.npmjs.com/package/openai?activeTab=code); [openai-node CHANGELOG](https://github.com/openai/openai-node/blob/master/CHANGELOG.md)). The repo's pinned `openai@7.32.0` already includes Luna and 6.1 Sol. Third-party trackers put Luna at **$0.10 in / $0.50 out per million tokens** and Sol at $2 / $10, with cached input at about 10% of list ([CloudZero](https://www.cloudzero.com/blog/openai-pricing/)). OpenAI's own pricing page was unreachable, so verify those figures before quoting them. Build on the Responses API. It supports `prompt_cache_key` plus `prompt_cache_diagnostics`, which reports misses caused by tool, text-format, reasoning-effort or service-tier changes ([openai responses.d.ts](https://www.npmjs.com/package/openai?activeTab=code)). Keep system prompts and tool lists byte-stable and first, put dynamic snapshots last, and show the cache-hit rate on the ops panel. The Batch API is about 50% off ([the-decoder](https://the-decoder.com/openai-introduces-batch-api-with-up-to-50-discount-for-asynchronous-tasks/)), but it is asynchronous. Merchant-level labeling costs cents, so Batch is only worth a slide as the backfill strategy.

### Framework choice and its tradeoff

The strongest recommendation is to build the Copilot on **Vercel AI SDK v7**: `ai`, `@ai-sdk/openai` and `@ai-sdk/react`. `ToolLoopAgent` with `useChat` gives streaming, tool-result parts rendered as React cards, and **built-in tool approval** that maps directly onto `draft_action` ([Vercel: AI SDK 6](https://vercel.com/blog/ai-sdk-6); [AI SDK docs](https://ai-sdk.dev/docs/ai-sdk-ui/generative-user-interfaces)). PLAN.md's hand-rolled OpenAI function-calling loop is simpler to reason about, but it leaves the team writing stream parsing, tool-call UI and approval state by hand on Wednesday. AI SDK v7 has two costs. It renamed many APIs (`stepCountIs` became `isStepCount`, and `toUIMessageStreamResponse` is deprecated), so most online examples are stale and the team should code against the docs bundled in `node_modules/ai/docs`. And earlier 7.x releases let a forged client message replay a "pre-approved" tool call; **recent 7.x re-validates approvals** and supports HMAC signing ([ai CHANGELOG](https://www.npmjs.com/package/ai?activeTab=code)). The OpenAI Agents SDK is the runner-up for teams that want OpenAI's trace viewer, but it is pre-1.0 and ships breaking minor versions ([@openai/agents](https://www.npmjs.com/package/@openai/agents)). Mastra and LangGraph add abstraction without solving a Runway-specific problem. Skip OpenAI's hosted Agents API, a beta since Sep 10, 2026, as too risky for three days.

Autopilot should **not** be a free-roaming agent. Run it as a fixed sequence: sync Rho, categorize new merchants, run the detectors, write the memo, file tasks. The LLM appears only in categorization and the memo, and Jira payloads are built from typed findings. That is the "plan-then-execute" pattern the prompt-injection literature recommends: committing to the steps before touching untrusted data means a malicious descriptor can change content but never the sequence of actions ([arXiv 2506.08837](https://arxiv.org/pdf/2506.08837v1.pdf)). It is also cheaper, faster and easier to log as a step timeline, which is the visible proof the Antler track wants. The research suggests Vercel's Workflow SDK (`workflow@5`, `WorkflowAgent`) for durable, retried steps ([workflow](https://www.npmjs.com/package/workflow); [AI SDK WorkflowAgent](https://ai-sdk.dev/docs/agents/workflow-agent)). For a 1–2 person team, a single Node route that writes each step to `agent_steps` is enough. On seed data the whole run finishes far inside Vercel's 300-second Hobby cap ([Vercel limits](https://vercel.com/docs/functions/limitations)). Durable workflows (Workflow SDK or Inngest) belong in production, where 12-month backfills and rate-limit waits outlast a single function.

### Security, observability and UI

Treat every descriptor as untrusted input. Categorization outputs are enums, so an injected "ignore previous instructions" can at worst mislabel one vendor. Copilot tools take zod-validated filters rather than raw SQL. Memo inputs go inside data-only tags and the output is checked against SQL. Tickets come from templates with an allowlisted project key, and `draft_action` requires human approval and is re-validated on the server ([LogRocket](https://blog.logrocket.com/protect-ai-agent-from-prompt-injection/)). Because the sandbox accepts any token, an env var is fine this week. In production, Rho tokens go in **Supabase Vault**, read through a `security definer` function granted only to the service role; pgsodium is pending deprecation ([Supabase pgsodium](https://supabase.com/docs/guides/database/extensions/pgsodium)).

For observability, the AI SDK emits OpenTelemetry spans that **Langfuse ingests natively** through `@langfuse/otel`. On serverless, spans are lost unless exported in `immediate` mode and flushed in `after()` ([@langfuse/otel](https://www.npmjs.com/package/@langfuse/otel)). Langfuse is about an hour of work and worth it only after the core loop runs. The in-database `agent_steps` table already gives judges a run timeline with tokens, latency and cost. For UI, use shadcn/ui with shadcn charts (Recharts 3) and AI Elements for the chat surface. Skip Tremor, which has not released since January 2025 ([npm: @tremor/react](https://www.npmjs.com/package/@tremor/react)). AI Elements will be deprecated at the end of November 2026 in favor of a shadcn-native version ([ai-elements](https://www.npmjs.com/package/ai-elements)). Copying its components into the repo sidesteps that.

## A tenant-ready schema costs one extra column per table today

### Money, sync and idempotency

Store money as `bigint` minor units plus a `char(3)` currency, never floats, following Stripe's integer convention ([Stripe](https://docs.stripe.com/currencies)) and Modern Treasury's use of integers with an exponent ([Modern Treasury](https://docs.moderntreasury.com/docs/currencies)). Keep Rho's sign (negative means money out) on `transactions`, store savings as positive `monthly_savings_minor`, and keep `numeric` for ratios and runway months. Sync state is a **date watermark with a 10–14 day lookback**, not a stored cursor, because Rho forbids storing cursors ([Rho docs: Pagination](https://docs.rho.co/docs/v1/pagination)). Advance the watermark only after the whole window succeeds, borrowing Plaid's commit-after-success discipline ([Plaid](https://plaid.com/docs/transactions/sync-migration/)). Every write is `INSERT ... ON CONFLICT (connection_id, provider_txn_id) DO UPDATE ... WHERE raw_hash IS DISTINCT FROM excluded.raw_hash`. Re-runs are then no-ops, and pending-to-settled changes and amount changes land in place. Pending rows that vanish inside the lookback window get `removed_at`, never a hard delete. Findings upsert on `unique(org_id, fingerprint)`, for example `price_creep:<vendor>:2026-09`, so **a dismissed finding stays dismissed** when the detectors run again.

### Tenancy, audit and agent telemetry

Put `org_id` on every table now, including child tables such as `agent_steps`, and enable RLS with `org_id in (select private.user_org_ids())`. The helper is a `security definer` function, and `auth.uid()` is wrapped in a select. Supabase reports **over 100x gains** from indexing policy columns and wrapping functions this way ([Supabase RLS performance](https://supabase.com/docs/guides/troubleshooting/rls-performance-and-best-practices-Z5Jjwv)). Analytics views must be created `with (security_invoker = true)`, or they bypass RLS. Users get SELECT only. Mutations such as accepting a finding or approving an action go through RPCs that validate the state transition and append an `entity_events` row in the same transaction. The rule that Autopilot can create only `draft` actions and `open` findings, never approve them, then holds **in the database, not just the prompt**. Model agent logs after the OpenTelemetry GenAI conventions, with `operation`, `model`, input and output tokens and latency per step ([OpenTelemetry GenAI spans](https://opentelemetry.io/docs/specs/semconv/gen-ai/gen-ai-spans)). Store cost as integer micro-dollars computed from a `model_prices` table, and keep prompt and response bodies in a separate short-retention payload table, since OTel treats content as opt-in PII. Export to Langfuse later is then a direct column mapping.

### Supabase operations

Run the demo project on **Pro, paid with the credits**. Free projects pause after seven days idle and pg_cron stops with them ([JetAdmin](https://www.jetadmin.io/blog/supabase-pricing-2026-guide-to-plans-limits-and-real-world-costs/); [runhooks](https://runhooks.app/blog/preventing-supabase-free-tier-pausing/)), and judging is on Oct 30. Declarative Schemas 2.0 with pg-delta became the CLI default on Oct 2, 2026 ([Supabase blog](https://supabase.com/blog/declarative-schemas-2-0-pg-delta)). It is weeks old, so review the generated SQL, and fall back to hand-written migrations if it misbehaves. For raw SQL from Vercel, use Supavisor transaction mode on port 6543 with prepared statements disabled ([Supabase](https://supabase.com/docs/guides/troubleshooting/disabling-prepared-statements-qL8lEL)). Better still, keep detector SQL in Postgres functions called through `supabase.rpc()`. For the live Autopilot timeline, `postgres_changes` filtered by `run_id` is enough for a single-tenant demo. Production should switch to trigger-driven Broadcast on private `org:<id>` topics, because `postgres_changes` processes events on a single thread ([Supabase Realtime benchmarks](https://supabase.com/docs/guides/realtime/benchmarks)). Edge Functions cap wall-clock time at 150s on Free and 400s on paid plans ([Supabase limits](https://supabase.com/docs/guides/functions/limits)), so production sync must run as chunked, self-re-enqueueing jobs.

## Conclusion

The research moves Runway's center of gravity. The defensible product is not detection, which Ramp, rhodesk and a dozen Claude skills already do. It is **pricing waste in runway days and turning it into owned, auditable work**, built on a bank that deliberately cannot act. Read-only Rho, enum-constrained LLM calls, a plan-then-execute Autopilot and database-enforced draft-only actions together form a coherent trust architecture. That story answers the "is this safe and is this real?" question better than any single feature, and it should lead the pitch alongside the eval table.

The other finding is that the hackathon build and the production system can share one schema if three habits start now: `org_id` on every row, fingerprinted and idempotent findings and tickets, and an OTel-shaped run log with integer costs. Two production problems still lack answers. One is zombie detection without usage data, which needs an SSO or Google Workspace signal or explicit user feedback. The other is real price benchmarks, which need either a Vendr partnership or enough tenants for anonymized cross-company medians. Those two gaps are where Runway can grow from a sharp demo into a product.
